## 1. Verdict

**The invariant layer is well-built and its two strongest guarantees are not actually
enforced. The plan is behind where the code is. Nothing has been measured.**

The good parts are genuinely good — `rounding.py` gets the polarity split right, the tests
assert derivations rather than values as §21.1 demands, and `tests/README.md`'s mutation
table is honest about its own blind spot. That work is not in question.

But four of the five HIGH findings below are the same shape, and it is the shape this
codebase exists to prevent:

| # | The stated guarantee | What is actually enforced |
|---|---|---|
| F1 | `Config` is frozen and validated; the hard caps are non-bypassable | `MODE_PRESETS` is a plain mutable dict read **live** on every lookup. One assignment raises a live config's risk-per-trade to 50% past a 2% "non-bypassable" cap |
| F2 | "No numeric literal for a registered threshold anywhere else in the codebase," enforced by a test | The test is blind to **7 of 29** parameters through a `Decimal.normalize()` bug. Six hardcoded literals injected into `gates.py` pass it |
| F3 | "Every construction path validates; there is no other" | `Config(values)` never range-validates. `max_spread_r = 99` is accepted and turns the spread gate off |
| F4 | "Polarity, not the call site, decides rounding" | The call site decides. `Config.polarity()` has zero callers; flipping a registry polarity breaks **no** test |

None of these is a subtle judgement call. Each was reproduced by running code, and each sits
directly under a sentence in `CLAUDE.md`, `architecture.md` or a module docstring asserting
the opposite. The documentation is what makes them dangerous: a reader is told the mechanism
is closed, so nobody looks.

Two further things pull the verdict down:

- **PLAN, PRD §19 and REVIEW-v1.3 all under-report what is built** (F7). The PLAN's own
  top-ranked item is marked "Not started" and is in fact done and green.
- **Nothing has been measured** (§6). Every threshold is calibrated against three
  hand-authored worked examples, and the Phase 2a data spike the PLAN has called the
  highest-value technical action since before any code existed is still not started.

**Is the project up to par?** For a Phase 1 invariant layer: yes on ambition, discipline and
tooling; not yet on enforcement. The five HIGH/MEDIUM-HIGH findings are perhaps a day of work
between them, and none requires a spec decision. After that it is up to par, and the binding
constraint becomes data, not code.

## 4. Findings

Severity is about consequence if the layer is built on, not about effort to fix.

### F1 — HIGH: `MODE_PRESETS` is a mutable module dict, read live, and it defeats the hard caps

`params.py` is aggressively immutable everywhere it is visible: frozen dataclasses, an
unconditional `MappingProxyType` copy, and three paragraphs (`:180-203`) explaining why each
was necessary. But `MODE_PRESETS` (`:147`), `HARD_CAPS` (`:163`) and `PARAMS` (`:82`) are
plain mutable module-level dicts, all exported in `__all__`, and `Config.__getitem__`
(`:218-224`) falls through to `MODE_PRESETS[self.mode]` **live** on every lookup rather than
copying at construction.

Reproduced:

```python
cfg = Config.default()                        # frozen, validated, coupling-checked
position_size(D("5.16"), D("5.04"), cfg)      # 2500 shares at 1% risk

MODE_PRESETS["experienced"]["max_risk_per_trade_pct"] = D("0.50")

cfg["max_risk_per_trade_pct"]                 # Decimal('0.50')  — same object
position_size(D("5.16"), D("5.04"), cfg)      # 10000 shares (only max_shares_per_order caps it)
HARD_CAPS["max_risk_per_trade_pct"]           # Decimal('0.02')  — the "non-bypassable" cap
```

Fifty percent of equity risked on one trade, through a config that has already passed every
validator, against a cap the PRD calls non-bypassable (§2, §7). No validator re-runs, because
none is on the read path.

This is strictly larger than F3: F3 needs you to construct a fresh `Config`, this mutates one
that already exists and is held by callers. It also makes `params.py:339` — the `HARD_CAPS`
violation branch F6 calls unreachable — the *only* way that branch can ever fire, and only
after the damage is done.

`test_config_values_cannot_be_mutated_in_place` and
`test_proxy_does_not_retain_a_live_handle_to_the_callers_dict` exist to close exactly this
class for `Config.values`. Neither covers the presets, and their presence is the reason it
reads as covered.

**Fix:** wrap all three dicts in `MappingProxyType` (and the inner preset dicts too — a proxy
over a dict of dicts still exposes mutable values), or resolve the preset into `values` at
construction. Add the mutation test.

### F2 — HIGH: the registry lint is blind to 7 of 29 parameters

`CLAUDE.md:43-45`, `CONTRIBUTING.md:13`, `architecture.md:46-47` and
`.cursor/rules/tradipy.mdc:14-16` all state the project's headline convention: no numeric
literal for a registered threshold may appear anywhere outside the registry, enforced by
`test_no_registered_literal_hardcoded_in_source`.

That test builds its search set at `test_parameter_registry.py:72-75` using
`str(p.default.normalize())`. For any default with trailing zeros, `Decimal.normalize()`
returns **scientific notation**, so the regex at `:91` searches source for strings that can
never occur:

| Parameter | Default | Searched for |
|---|---|---|
| `start_of_day_equity` | 30000 | `Decimal("3E+4")` |
| `max_shares_per_order` | 10000 | `Decimal("1E+4")` |
| `rvol_lookback_days` | 30 | `Decimal("3E+1")` |
| `max_float_shares` | 20000000 | `Decimal("2E+7")` |
| `max_price` | 20.00 | `Decimal("2E+1")` |
| `min_adv_shares` | 500000 | `Decimal("5E+5")` |
| `bar_close_grace_ms` | 750 | `Decimal("7.5E+2")` |

Verified by mutation: six hardcoded literals injected into `gates.py` — `Decimal("30000")`,
`Decimal("10000")`, `Decimal("500000")`, `Decimal("30")`, `Decimal("750")`, `Decimal("20.00")`
— and the lint **passes**.

Among the blinded parameters is `start_of_day_equity`, the denominator of every position
size. This is the project's central convention with a hole in its only enforcement mechanism,
and it is the same defect shape the codebase was written to prevent — a rule that is correct,
documented, believed to be enforced, and is not.

**Fix:** search for both forms, or drop `.normalize()` and use `str(p.default)` plus a
trailing-zero variant. Then re-run the mutation check in `tests/README.md`; several of its
15 rows may be scoring against a lint that could not have caught them.

### F3 — HIGH: `Config(values)` skips per-parameter range validation

`params.py:182` promises: *"A validated parameter set. Every construction path validates;
there is no other."* `__post_init__` (`:208-216`) does three things — freeze a copy, reject a
partial mapping, call `validate_couplings`. It never calls `Param.validate` (`:61-65`). Range
validation happens **only** in `with_overrides` (`:246`).

Reproduced:

```python
vals = {n: p.default for n, p in PARAMS.items()}
vals["max_spread_r"] = Decimal("99")      # legal range [0.05, 0.50]
cfg = Config(vals)                        # accepted
spread_caps(Decimal("5.00"), Decimal("0.15"), cfg)
# SpreadCaps(scan=Decimal('0.02'), signal=Decimal('14.85'))
```

The §3.1.3 signal-time spread gate is off. Nothing raises, nothing warns.

What makes this more than a missing check is that
`test_direct_construction_cannot_skip_coupling_validation` (`test_boundary.py:539`) exists
specifically to prove this path is closed. It closes the coupling half, leaves the range half
open, and its docstring — *"no construction path can route around it"* — reads as though both
were covered.

**Fix:** call `PARAMS[name].validate(value)` for every entry in `__post_init__`, before
`validate_couplings`. Extend that test. Correct `params.py:182` and `architecture.md:51-53`.

### F4 — HIGH: registry polarity is not what decides rounding

`CLAUDE.md:46-47`: *"Polarity, not the call site, decides rounding."* `rounding.py:41-47`:
*"PRD §20.13 requires every threshold to be classified before a rounding function is
chosen."*

In practice `gates.py` passes a **literal** at each of five call sites — `Polarity.MAXIMUM` at
`:80` and `:81`, `Polarity.MINIMUM` at `:109`, `:146` and `:152`. `Config.polarity()`
(`params.py:226-233`), the accessor built for exactly this, has **zero callers** in `src/`,
`tests/` or `scripts/`; coverage confirms `:227-233` never execute.

So polarity has two independent sources of truth — the registry field and the literal in
`gates.py` — and nothing reconciles them. Verified by mutation: flipping `max_spread_abs` to
`Polarity.MINIMUM` in the registry leaves `spread_caps` flooring as before and **all 63 tests
still pass.** Not one notices, `test_every_gate_parameter_declares_a_polarity` included — it
asserts a polarity is *present*, never that it is *used*.

This is "one definition per threshold" violated for polarity instead of for a number: the
v1.3.1 class, reproduced inside the mechanism built to close it.

Related: only 13 of 29 parameters declare a polarity. `sep_cost_multiple`, `min_sep_r` and
`t1_r_multiple` all feed `round_threshold(..., Polarity.MINIMUM)` through `min_separation` and
`required_room` and declare none.

**Fix:** have `gates.py` read `cfg.polarity(name)` rather than naming a member. Add a test
asserting each gate's rounding direction follows its registry declaration. Declare polarity on
the three parameters above.

### F5 — MEDIUM-HIGH: `mode` default contradicts PRD §2.0, and `beginner` has zero tests

`PRD.md:84` — `| mode | beginner | beginner | experienced | Preset bundle, below |`. Code —
`params.py:206` and `:236` both default to `"experienced"`.

The consequences are not cosmetic: `max_risk_per_trade_pct` 0.5% → 1.0%, `daily_loss_pct`
2% → 3%, `max_open_positions` 1 → 3, `max_consecutive_losses` 2 → 3. On the §3.2 Bull Flag
example, position size is 1,250 shares under the PRD's declared default and 2,500 under the
code's.

The PRD is itself inconsistent: every worked example (§2.2, §3.2, §3.3, §3.4) computes risk as
1% × $30,000, i.e. the *experienced* preset. So the code follows the examples and contradicts
the declared default, and one of the two is wrong. Per `CLAUDE.md:92-94` this is a spec
question and should be raised, not resolved in code. It has not been raised anywhere.

Separately: **`mode` is entirely untested.** Every test uses `Config.default(mode=
"experienced")` (`test_worked_examples.py:34`, `test_boundary.py:44`, `:516`). Nothing ever
constructs a beginner config, so `MODE_PRESETS["beginner"]` is never read — against a mode the
PRD says is the default.

### F6 — MEDIUM: the "non-bypassable" hard caps are checked against constants that cannot vary

`validate_couplings` (`params.py:337-342`) checks `MODE_PRESETS[cfg.mode][name] > cap` for each
`HARD_CAPS` entry. The loop runs on every construction, but the violation branch at `:339`
cannot be reached through any supported path: `MODE_PRESETS` is a module constant and
`with_overrides` rejects any name not in `PARAMS`:

```python
Config.default().with_overrides(max_risk_per_trade_pct="0.05")
# KeyError: 'max_risk_per_trade_pct is not a registered parameter (PRD §2 / §2.0)'
```

Coverage confirms `:339` never executes. The only route that reaches it is F1's mutation, by
which point the config has already been compromised.

## 6. The risk the findings list does not capture

Five review rounds and one implementation round have produced a 2,271-line specification and
a 177-statement library, against **zero measured market data**.

The invariant layer is calibrated entirely against three hand-authored worked examples. Its
load-bearing constants are unmeasured, and the PLAN says so:

| Constant | Value | Basis | PLAN says |
|---|---|---|---|
| `max_spread_r` | 0.15 | 3 worked examples | A21: "may reject most cheap-stock setups… could effectively disable VWAP Reclaim" |
| `est_round_trip_cost_per_share` | $0.015 | estimate | "unmeasured. Calibrate from real paper fills" |
| `sep_cost_multiple` | 3.0 | judgement | drives the D17 separation floor |
| `impact_coefficient` | 1.0 | "unvalidated" | biases §18.7's viability gate toward "go" |

The test suite proves these are used *consistently*. It cannot say whether 0.15 admits 90% of
qualifying setups or 5%. Two of the four documented open findings — the $1.00–$1.99 band in
both its forms — are unresolvable without a real spread distribution.

`PLAN.md:260` has called the Phase 2a data spike the "highest-value technical action" since
before any code existed, notes that vendor lead times are weeks, and warns that a negative
result rewrites PRD §4. It remains not started, and has now been passed over once in favour of
code. The strategy-has-no-edge risk (`PLAN.md:319`) is still the top risk and nothing in this
repository has moved it.

The second uncaptured risk is procedural: **no reader without prior context has reviewed any
version of the PRD** (`PRD.md:1886`, `REVIEW-v1.3.md:201`, `PLAN.md:254`). Each of the four
found classes was found by a cold read. This review is not one.
