### G1 — MEDIUM: 17 of 47 parameters have no consumer, and the registry does not say which

The prior round measured this once — *"15 of 29 registered parameters have a consumer in `src/`"* —
and named two that did not, both since wired. Nothing in `docs/` states the current figure. From an
exhaustive scan of every `params.PARAMS` key against every other module in `src/tradipy/`:

| Group | Parameters with no reference outside `params.py` |
|---|---|
| §4.2 scanner filters (7) | `min_price`, `max_price`, `min_gap_daily_pct`, `min_gap_premarket_pct`, `min_rvol`, `min_adv_shares`, `min_premarket_volume` |
| §2 entry-extension thresholds (3) | `max_vwap_extension_pct`, `max_vwap_extension_open_pct`, `hod_proximity_pct` |
| §7 risk limits (5) | `daily_loss_pct`, `max_open_positions`, `max_consecutive_losses`, `session_dd_pct`, `multi_day_dd_pct` |
| §20.1 (1) | `bar_close_grace_ms` |
| §20.7 (1) | `rvol_lookback_days` |

**Two** of the five §7 rows — `daily_loss_pct` and `max_open_positions` — are read inside
`params.validate_couplings`, against the three-key `HARD_CAPS` mapping. They are validated once
at construction and never consulted again. The remaining three (`max_consecutive_losses`,
`session_dd_pct`, `multi_day_dd_pct`) are read nowhere outside `params.py` at all, not even
there. That gradient is exactly the problem: a parameter can be range-checked, cap-checked and
cited, and still gate nothing — and from the registry, all five look identical.

**Why it matters.** Not because the parameters are premature — registering §4 and §7 ahead of
their engines is the right call and is what makes D27 possible. It matters because the registry
is the artifact this project points at when asked "is this rule implemented?", and it answers
"registered" to a question about enforcement. The same conflation is what F4 was.

**Proposed disposition.** Add a field to `Param` — `enforced_by: str | None`, naming the module
or function that reads it, `None` for "awaiting a layer" — and a registry test asserting that
every parameter with a non-`None` value really is referenced there, and every `None` one really
is not. That test is cheap, it is the guard-on-the-guard shape the lint already uses, and it
converts a fact discoverable only by grep into one the registry states. It also fails loudly the
day a scanner is built and the field is not updated, which is the failure mode worth buying.
**Not** a behaviour change; no threshold moves.

### G2 — MEDIUM (spec question): `daily_loss_pct` is NON-BYPASSABLE with no enforcement point

§7's rule table has an explicit **Bypassable** column, and it does most of the work here. Of the
six registered risk settings:

| §7 limit | §7's Bypassable column | Legal range in code | Enforcement point in code |
|---|---|---|---|
| `max_risk_per_trade_pct` | **No (NON-BYPASSABLE)** | ✓ 0.25–2% (D27) | ✓ `gates.position_size` |
| `daily_loss_pct` | **No (NON-BYPASSABLE)** | ✓ 1–5% (D27) | **none** |
| `max_open_positions` | Configurable max only | ✓ 1–3 (D27) | none |
| `max_consecutive_losses` | Yes (2–5 range) | ✓ 2–5 (D27) | none |
| `session_dd_pct`, `multi_day_dd_pct` | Yes | ✓ | none |

So the finding is narrower and sharper than "four unenforced non-bypassable limits," which is
what the first draft of this review said by reading §2's configurability column and never opening
§7's. **It is one limit: `daily_loss_pct`.** The other three are bypassable by §7's own
declaration, and their absence from the code is unremarkable.

`daily_loss_pct` is the one D16 froze the denominator for, the one §7 pairs with risk-per-trade
as the two hard rules, and nothing in the package tracks realized P&L, so nothing *could* enforce
it — it needs the state layer §20.12 describes and no module implements. That is a scope
boundary, not a bug.

It is a finding anyway, on the grounds `CLAUDE.md` convention 6 states: *"for any sentence of the
form 'X cannot happen', write the test that attempts X and asserts it fails."* The daily loss
limit has no such test and cannot have one. D27's achievement was giving it a legal range and a
cap check; the missing half is that a range without an enforcement point is not what §7 means by
non-bypassable. The prior round found the inverse and called it F6 — a cap guarding an immovable
constant. This is a cap guarding a movable value that nothing reads.

Worth noting that §7's non-bypassable set is larger than these two — the PDT check and the
emergency kill switch are marked No, the min R:R ratio likewise, and the spread check reads
*"Bounds only (0.05–0.50); cannot be disabled"* — and the last two **are** enforced, in
`gates.check_spread` and `gates.required_room`/`check_room`. The gap is specific, not systemic.

**Raise, do not resolve.** §7 already has an *Enforcement Point* column; the question is whether
`daily_loss_pct`'s cell should be qualified — *"Continuous (1 sec) + post-fill — Phase 6"* rather
than *"Continuous (1 sec) + post-fill"* — so that the deferral is visible in the normative text
that asserts the guarantee. The alternative is to leave §7 alone and note it only in `params.py`,
which keeps an unqualified non-bypassable claim in the document. The first is better; it is still a spec edit to
a row the PRD calls hard, and not a code decision.

### G3 — LOW: `Reject` implements 6 of ~23 spec-named codes, and nothing compares the two sets

`rejects.Reject` has `SPREAD_TOO_WIDE`, `INSUFFICIENT_ROOM`, `TARGETS_TOO_CLOSE`,
`STOP_TOO_WIDE`, `QUOTE_STALE`, `QUOTE_CROSSED`, `DATA_QUALITY_DEGRADED`. The spec names at least
**23** codes: §4.2's fourteen, `INSUFFICIENT_ROOM` and `TARGETS_TOO_CLOSE` in §3.1.2,
`QUOTE_STALE`, `QUOTE_CROSSED`, `DATA_QUALITY_DEGRADED` and `SPREAD_ESTIMATED` in §20.9/§20.14,
`SUPERSEDED` in §20.11, `ATR_INSUFFICIENT_HISTORY` in §20.15, `BAR_REVISED` in §20.1.

**Downgraded from LOW-MEDIUM.** The first draft of this finding claimed the enum implemented four
spec codes and that its other three were code-originated with nothing marking them as such. Both
halves were wrong: `PRD.md:241` assigns `INSUFFICIENT_ROOM` and `TARGETS_TOO_CLOSE` explicitly, so
the enum implements **six** of the spec's codes; and the one member the PRD genuinely never names,
`STOP_TOO_WIDE`, is already marked in exactly the way the finding asked for —
`rejects.py:35-39` says *"The PRD states the rule … without naming a code; this name is the
implementation's."* Which is `Param.source`'s convention, applied to an enum, before anyone asked.

What survives is the mechanical half. **Nothing compares the enum to the spec's namespace in
either direction**, so the day a scanner is built there is no check that its codes are the codes
§4.2 names, and no check today that a §4.2 code has not been quietly renamed. The registry lint
does this job for thresholds and has caught a real defect doing it. The convention this project
would ordinarily apply — one definition, referenced by name — is not applied to the reject codes,
and the reason is only that nothing yet consumes them.

**Proposed disposition.** A test that extracts the rejection-code column from §4.2 and the
`SUPERSEDED`-style codes from §20 by the same prose-scanning technique
`test_parameter_registry.py` already uses on §2, and asserts every implemented code is spelled
as the PRD spells it — with an explicit frozen list of the not-yet-implemented ones and of the
code-originated members, so the test fails when either list is wrong rather than demanding the
enum be complete. Same shape as the 68-entry baseline, same reason.

### G5 — LOW: `select_flagpole`'s qualification hook has no shipped caller

`bars.select_flagpole(bars, candidates, qualifies=None)` takes the §3.2 criterion-2 predicate as
its third parameter (`bars.py:95-99`). `poc.bull_flag_geometry` calls `flagpole_ending_at`
directly (`poc.py:266-298`), so in the only composed path in the package **no qualification
runs**. §20.4 states its detection rule is *subject to* §3.2 criterion 2, and the demo's geometry
therefore reports a flagpole the setup criteria have not been applied to.

Low because the demo's eight-bar fixture does satisfy the criteria — the printed retrace of
28.6% and flag/pole volume of 0.55 are both inside their §3.2 bounds — and because the criteria
are checked in `tests/`. But a hook whose predicate no shipped caller supplies is F4's shape,
and the fixture passing is not evidence the hook is wired. Note that wiring it means threading
`green_runs` output through `bull_flag_geometry` as the `candidates` argument, which is a slightly
larger change than the one-line call swap it looks like.

Also, unspecified: `select_flagpole`'s third-level tie-break (equal length *and* equal volume)
resolves to the earliest index, where §20.4 gives two tie-break levels and stops. The code
already says so — *"§20.4 does not say, and picking deterministically beats picking
arbitrarily"* (`bars.py:102-104`) — so the remaining gap is a sentence in §20.4, not a comment.
The first draft of this finding asked for the comment that was already there, which is what
comes of reading a signature and not the body.

### G6 — LOW: `is_whole_tick` has no library caller

§20.13 calls whole-tick prices a universal requirement. `rounding.is_whole_tick` exists, is
correct, and is called only from `tests/`. Nothing at runtime asserts that a price about to be
submitted is a whole tick.

One severity below F4 because every price the package *produces* goes through `_rounded` or
`floor_to_tick`/`ceil_to_tick` and is therefore whole-tick by construction — the checker is
redundant today. It stops being redundant at the first price that arrives from outside:
`Candidate.entry`, `raw_stop`, `structural_target` and `resistance` (`poc.py:47-50`) plus a
`Quote`'s `bid` and `ask` are all caller-supplied and unvalidated. An assertion at the boundary
of `poc.evaluate` and `quotes.check_quote` would close it. These six are the same class of
unvalidated input as `mode` was in F9.

### G7 — LOW: "153 cases" and 117 test functions

The PLAN's fixture-suite row and root `CHANGELOG.md:119` cite *"153 cases, 99% line and branch
coverage, 47/47 mutations caught."* (The PRD does not — `grep -n "153" docs/PRD.md` is empty, and
the first draft of this finding said it did.) A static count gives **117 `def test_` functions** —
`test_boundary` 36, `test_computations` 22, `test_poc` 18, `test_enforcement` 17,
`test_worked_examples` 13, `test_parameter_registry` 11. Parametrization plausibly accounts for
the difference, and I could not run the suite to confirm 153.

The finding is not that the number is wrong — it is that the PLAN cites it as evidence without
saying whether it counts functions or collected cases, and F7 was about status claims that are
not checkable. Say "153 collected cases (117 test functions)."

One reason to actually re-measure rather than just relabel: the prior round reported 41 functions
/ 63 cases, a ratio of 1.54. 153/117 is 1.31. The suite grew by 76 functions and became *less*
parametrized per function, which is plausible — the enforcement fixtures are mostly one-shot
mutations — but it is also what a stale case count looks like.
